# 记忆系统设计：TencentDB Agent Memory 的 DSH 改写

日期：2026-08-20
状态：已定稿，待实施
源项目：TencentCloud/TencentDB-Agent-Memory（MIT，v0.3.5，vendor 于本仓）

## 1. 背景

DSH 现有记忆机制是 compaction（压缩总结）：单个会话窗口快满（默认 80%）时，把老对话压成一次性摘要腾地方。它只管"窗口内不断线"，摘要用完即弃，**跨会话全部遗忘**。

腾讯开源的 TencentDB Agent Memory 是完整的长期记忆系统（分层沉淀 + 混合检索 + 分层注入），但它是一整套外部服务（核心 8420 / 代理 8096 / 知识 8421 / 面板 8123），直接接入有四条死结：

1. 外部服务依赖重（Docker 三件套 + 可选 Redis/ClickHouse/COS/计费/观测），与本地单机 profile 形态不搭；
2. 接入方式是劫持请求路径（baseURL 指到它的代理），与我们的模型方案/参数透传/换件链路冲突；
3. 身份体系对不上（它的 user/team/agent/ACL 是独立多租户体系）；
4. 注入粒度粗（代理层对整个 system prompt 塞三块，我们是逐请求精确控制的拦截链）。

**决策：不接入，改写为 DSH 插件。**

## 2. 核心原则

1. **改写不是重写**：vendor 腾讯核心引擎源码进本仓改造，机制代码保真；重写必降级。
2. **改写不是引包**：不依赖其 npm 包，源码在仓内完全可控。
3. **不降级**：每个机制交付时给"原版代码位置 ↔ 本仓对应物 ↔ 跑通证据"对照，对不上即打回。
4. **只砍基础设施，不砍机制**：砍除项显式列清单，逐条经批准。

## 3. 调研结论（事实层）

### 3.1 腾讯引擎的可适配性（已查证）

- 核心类 `TdaiCore` + `HostAdapter` 接口（约 50 行）+ `LLMRunner` 接口（单方法 `run`）。源码注释明示："核心只依赖这些接口——从不依赖特定宿主"。
- gateway（HTTP 服务层）对 core 单向依赖，core 反向零依赖；官方自身即以独立适配器驱动同一引擎。
- LLM 调用全经工厂注入，全库无一处直接发请求。
- 公开入口齐全：`handleTurnCommitted`（每轮喂数据）、`handleBeforeRecall`（召回）、`runL1/L2/L3`（手动提炼）。
- 配置为纯对象注入，不读 yaml；数据目录由 HostAdapter 指定。
- MIT 许可：vendor 合法，义务为保留版权头。

### 3.2 记忆分层机制

| 层 | 内容 | 提取方式 | 时延 |
|---|---|---|---|
| L0 | 原始对话 | 引擎自存（我们喂数据） | 即时 |
| L1 原子 | 事实/偏好/约束，三类（人格/情景/指令），带优先级打分与来源溯源 | 单次 LLM 调用出 JSON，单次上限 20 条 | 秒级 |
| L2 场景 | 叙事文档（非清单），UPDATE>MERGE>CREATE | agent 式多轮工具调用 + 沙箱 + 软删除 + 失败回滚 | 分钟级 |
| L3 画像 | 稳定画像，限 2000 字符 | agent 式，四层深度扫描 | 约 50 轮触发 |

级联：每 5 轮触发 L1 → L1 完成推 L2 → L2 完成推 L3。L1 去重为两阶段（机器候选召回 → LLM 批量判定存/合并/丢）。

### 3.3 检索与注入

- 检索：BM25 默认开（SQLite FTS5），向量默认关（留配置口），混合时 RRF 融合；分数阈值、条数上限、字符预算、超时——记忆不许占满上下文。
- 分层召回注入：L3 画像 + L2 场景导航 → 系统提示尾部（稳定吃缓存）；L1 动态事实 → 用户消息前缀（每轮变）；深层细节 → 给主代理两个工具（查记忆/查原对话，限 3 次）。

### 3.4 概念模型

- Team = 顶层归属边界；Agent = **持久"记忆人格载体"**（有人设、有绑定资产，自己不跑循环，客户端借它的身份干活，成果记到它头上）；Task = 持久业务任务（目标/状态/关联 Agent/可选记忆过滤维度）。
- 记忆归属 per-(team, agent)：L0/L1 带全维度标签（含 user/session/task），L2/L3 刻意忽略 user/session，跨会话累积。

## 4. 概念映射（DSH 侧）

| TencentDB | DSH |
|---|---|
| Team | 团队 |
| Agent（记忆人格载体） | **团队编制表里的角色（role，soul）**——持久身份+人设 prompt+绑定执行体（subagent），与 TencentDB Agent 的"人格载体不跑循环"同构：我们的角色定义人格，执行由绑定的子代理身体承担（souls bound to bodies） |
| Task | **任务（新增实体，见 §7 F10）** |
| user | 单机固定用户 |
| （主会话） | **team 本身的记忆**——主代理即团队的对外代表，主会话沉淀的记忆归属团队级（跨角色、跨会话共享的团队记忆）。TencentDB 侧对应"每个 Team 自动建 default Agent"的机制，我们直接以 team 为归属维度 |

**角色记忆策略挂钩**：编制表角色已有 `memory: persistent | one-shot` 字段——persistent 角色的记忆沉淀进记忆系统（跨派遣累积）；one-shot 角色每次派遣全新、不沉淀（与其"对之前派遣一无所知"的语义一致）。记忆归属为 per-(team, role)。

### 4.1 三维正交归属模型

team（团队经验/协作方式）与 project（项目事实/场景）**独立变化、必须正交**：同一 team 跨项目复用其人格与经验，同一项目跨 team 保留其事实。归属三维：

| 维度 | 内容 | 生命周期 |
|---|---|---|
| team 记忆 | 团队协作方式、团队级经验 | 跟 team 走，跨项目累积 |
| role 记忆 | 角色人格与角色技能 | 跟角色走，跨项目累积 |
| project 记忆 | 项目事实与场景（"这个仓库鉴权不能动"） | 跟工作区走，跨 team 保留 |

召回三路汇聚：当前会话上下文 = team 记忆 + role 记忆 + project 记忆。交叉经验（"lead 在 X 项目踩的坑"）内容上是项目事实→入 project 库（换 team 来干仍可见），来源标签记录攒它的 team/role。

实现：三个并行 scope（team / team+role / project），召回各查再合并；L1 把 project 打成过滤标签（与 task 同待遇），不拆库。

### 4.2 注入时机与缓存设计

**核心原则（用户拍板）：注入的价值 = 记忆里"不在当前上下文中的信息"。** 由此推出四阶段时机模型：

| 阶段 | 上下文内容 | 注入动作 |
|---|---|---|
| 新会话首轮 | 历史为空 | **注入**——跨会话复用的入口（记忆即新会话的前世） |
| 会话进行中（未达阈值） | 全量历史在 | **不注入任何记忆**（含外部来源）——本会话沉淀的记忆注入即冗余；仅后台异步提炼 |
| 达阈值重组 | 换血时刻，前缀缓存必废 | **切换到记忆组合并装最新**——额外缓存成本为零 |
| 重组之后 | 老历史已被记忆组合替代 | **持续注入**（L1 每轮检索开始有意义） |

缓存设计因此大幅简化：

- **会话前期**：无注入，system 恒定，前缀缓存零风险；
- **重组点**：一次性换血（本来就是大失效，装新记忆零额外成本）；
- **重组后**：拼接按变化频率——
  ```
  system（官方提示词）
  ├─ team L3 → project L3 → role L3      ← 画像，慢变
  ├─ team L2导航 → project L2导航 → role L2导航  ← 导航，中频
  ├─ 历史消息（记忆组合 + 近期原文）
  └─ 当前消息（L1 三维混查前缀）           ← 每轮变，只影响当轮增量
  ```
  主会话五段（无 role L3），子会话六段全。L1 三维混查放最后用户消息前缀——每轮变只影响新消息增量，历史缓存不动。

此前讨论过的"会话级快照/导航懒更新"机制**作废**——前期不注入使内容流变的缓存问题根本不存在，无需额外机制。

预算：三路合计仍受总预算硬限（vendor 机制保留），内部分配比例可配（默认 role > project > team——离当前任务越近给越多）。

### 4.3 会话内历史：分层摘要与统一注入上限（定稿）

**两类内容，两种管辖**：

```
当前消息
+ 历史原文（近期未被压缩部分）      —— 不进阈值：原文是原材料，不存在"注入"
+ 历史会话记忆（分层摘要）          —— 进阈值：压缩产物，属注入内容
+ 跨会话记忆（三维画像/导航/事实）   —— 进阈值：注入内容
```

**历史概要与跨会话记忆不是一种东西**：概要是**时间线的浓缩**（"第 1-50 轮做了 X"），服务当前会话继续；跨会话记忆是**知识的沉淀**（事实/场景/画像按主题与归属组织），服务跨会话复用。两套机制独立，共享统一注入上限。

**两个独立触发**：

1. **原文压缩触发**：历史原文逼近窗口容量 → 老原文压成分层摘要（近的细、远的粗），摘要进上下文（开始占阈值预算），原文撤出上下文但**持久化存档**；
2. **统一注入上限触发**：分层摘要 + 跨会话记忆合计达到注入上限 → **递归粗化**（细摘要并粗摘要、粗摘要并更粗摘要）——**信息不丢，只丢粒度**（单模式；曾讨论的可裁剪模式已废弃）。

**摘要持久化（每层必存）**：

- 会话中断/重启恢复——不用重算；
- **补召**：粗化过头时发现某段需要更细粒度，从存储里逐级补回——
  ```
  上下文里的粗摘要 ← 存储的细摘要 ← 存储的更细摘要 ← L0 原文
  ```
  补召链路全程有据，也是工具回查的存储基础；
- 跨会话引用（新会话查"上次聊到哪"）。

**与时机模型的衔接（修正 §4.2 的"切换"表述）**：达阈值重组不是"老原文请出上下文只留 16%"，而是"老原文压成分层摘要、历史在上下文里**全程有代表**"——原文层面只保留近期段，信息层面从头到现在不丢。

## 5. 重大架构决策：原版 compaction 退役，统一记忆接管

**理由**：compaction 与腾讯记忆的 L2 层干的是同一件事（浓缩历史），两套并存必然打架（"摘要的摘要"）。腾讯记忆的 L3+L2+L1+近期 L0 组合即可还原会话上下文，且压缩摘要本质是降级版 L2。

**统一后的行为**（按 §4.3 定稿结构）：

- 窗口到阈值：不再临时调模型压一次性摘要，改为**分层压缩**——老原文压成分层摘要（可多级，递归粗化），历史在上下文里全程有代表，近期原文保留；
- 溢出抢救：同理，加深粗化层级后重试；
- 异步滞后（跨会话提炼未跟上）：压力触发时**先同步补一次提炼**再粗化（成本与原 compaction 单次调用打平）；
- 冷启动（新会话尚无记忆就爆窗）：首次触发时同步做首次提炼+压缩。

**风险（实施期必须实测验证）**：

1. 分层摘要保真度：递归粗化后，coding 任务状态（改了哪些文件、进行到哪步）在各粒度层的完整度——实测验收；
2. 冷启动边界的用户体验；
3. 补召链路的实效（粗化后需要细节时，从存储补回的速度与准确性）。

## 7. 融合点清单

**F1 宿主挂载**：标准 bundle 形态，apply 时初始化 `TdaiCore` + 我们的 HostAdapter（数据目录/日志/配置由我们注入）。patch 行挂载，热升级路径。

**F2 L0 记录**：引擎自存（vendor 保留，查原对话工具依赖它）。我们负责喂数据：每轮对话完成，把新消息送入引擎公开入口。数据源 = DSH 会话事件流。

**F3 触发接线**：DSH 会话每轮结束 → `handleTurnCommitted`（带归属坐标：团队/角色/任务/会话）。引擎内部的计数、级联、锁全部 vendor 保留。

**F4 LLM 通道**：实现其 `LLMRunner.run`（单方法），背后接 `ctx.llm.stream`——**提炼走模型方案系统，可单配便宜方案**（如 venus flash），不烧对话模型的钱。三层提炼全经此通道。

**F5 召回注入**：挂 `agent/request` 拦截链（与模型方案 merge 同层）。**按 §4.2 时机模型执行**：新会话首轮注入、会话前期不注入、达阈值重组时切换并装最新、重组后持续注入。分层：画像+场景导航 → 系统提示尾；L1 三维混查 → 用户消息前缀。预算硬限 vendor 保留。merge 管模型路由、注入管消息内容，互不冲突。

**F6 深层回查**：引擎的两个查询能力注册为 DSH 工具（查记忆/查原对话），主代理需要细节时自行调用，限 3 次。

**F7 存储**：数据目录 `~/.dsh/memory/`：SQLite（结构数据+全文检索）+ 本地文件（场景/画像）。原生依赖（sqlite-vec、jieba）随 bundle 声明、reconcile 安装。云后端全裁。

**F8 身份坐标系**：团队=当前团队；角色=编制表 role（其绑定的子代理身体执行）；用户=单机固定；主会话=默认"主代理"身份。**不抄它的 4 步表单**——身份从会话上下文自动推导。

**F9 管理界面**：设置页新增「记忆」区块（与模型方案区块同架构，client inject + wire `/memory`）：资产按 团队×角色 分组（原子/场景/画像）、查看、删除、绑定角色（装配规则）、提炼状态可见、任务列表。

**F10 任务实体（新增）**：本地任务表——标题/目标/状态（进行中/完成）/负责子代理（含任务内角色）。两入口：管理界面手动建 + 主代理工具建。委派挂任务、会话挂任务、任务成为记忆过滤维度（只筛选不改变归属）。外部任务源（TAPD/GitHub）留口不做。

**F11 配置**：settings.yaml bundle 命名空间——开关、提炼模型方案 id、阈值（默认沿用引擎）。

## 9. 不降级验收对照（交付硬标准）

每机制交付时必须给出"原版代码位置 ↔ 本仓对应物 ↔ 跑通证据"：

- L0 记录与增量游标
- L1 原子提取（单次 JSON、三类、打分、溯源、上限 20）
- L1 去重两阶段（候选召回 → LLM 批量判定）
- L2 场景多轮整合（UPDATE>MERGE>CREATE、沙箱、软删除、失败回滚、容量预警）——**最易降级点，纪律写死：必须多轮**

- 级联调度（L1→L2→L3）与会话级锁
- 检索（BM25 + 阈值 + 条数/字符预算 + 超时）
- 分层注入（系统尾/用户前缀/工具回查限次）
- 统一接管后的窗口切换（压力/溢出/冷启动三路径）

## 11. 风险

1. 原生模块（sqlite-vec/jieba）需 profile 环境可编译/有预编译产物；装不上先关向量，纯 BM25 照跑；
2. Node ≥22.16（当前满足）；
3. vendor 后跟随上游升级靠手动；
4. L2 保真度与冷启动（见 §5）；
5. 统一接管后 compaction 相关官方测试/行为变化需全量回归。
